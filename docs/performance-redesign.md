## Что реализовано на этапе 0

- Core: новый необязательный `ShadowBakeProbe.detailedTimings()`; интервалы
  `bake-spot-copy` и `bake-point-copy` охватывают восстановление static→live,
  включая частичные прямоугольники и отдельные грани. Старые реализации probe
  получают прежнее разбиение, поскольку default возвращает false.
- Addon: асинхронные GL query объединяются по кадру, в котором отправлены команды.
  Повторяющиеся интервалы суммируются. Например, 25 копий по 0,1 мс дают 2,5 мс
  на кадр. Старое усреднение по отдельным query для такого разбиения было неверным.
- Время `bake` вычисляется отдельно для каждого полного кадра, затем считаются
  среднее, медиана, p95 (nearest rank) и максимум. Кадры без конкретной операции
  учитываются нулём; кадры с потерянным/зависшим/конфликтующим query исключаются
  целиком и отмечаются как rejected. Это не восстановление потерянного замера.
- Смена мира, пересоздание Iris-программ и переключение профайлера сбрасывают
  сессию и старые query. Незавершённая GL-скобка закрывается; ошибки pipeline
  помечают кадр неполным. Чтение GPU выполняется только после RESULT_AVAILABLE.
- Обычный профайлер теперь пассивен. Автоматический перебор VL, который меняет
  флаги эффектов, запускается только через `-Dirlite.profileVlSweep=true`.
- Опциональный CSV хранит сырые измерения по кадрам и счётчики работы; JSON рядом
  фиксирует пак, fallback Iris, ресурс и SHA-256 core-класса, версию аддона, GPU,
  разрешение, камеру и основные параметры света. В логе `profile-source` — хеши
  assembled ProgramSource при создании fullscreen-программ Iris.
- Скрипты делают снимок доставки и считают итоговые метрики за выбранное окно
  из сырых кадров. Усреднение готовых p95 из секундных окон не используется.

## Что означают метрики

| Имя | Измеряемая работа |
| --- | --- |
| `bake-spot`, `bake-point` | Draw, clear и настройка проходов; без static→live copy при detailed=true |
| `bake-spot-copy`, `bake-point-copy` | Static→live copy; сумма всех интервалов за кадр |
| `bake-spot-pyr`, `bake-point-pyr` | Min/max pyramid |
| `bake-spot-evsm`, `bake-point-evsm` | Полные существующие цепочки moment-фильтров; имя point сохранено, внутри используется MSM |
| `bake` | Сумма всех `bake-*` одного кадра, включая head/tail |
| `deferred2` | Fullscreen VL-pass эталонного CR, целиком |
| `composite1` и прочие имена Iris | Полный соответствующий fullscreen-проход, включая работу самого shaderpack |
| `cpu/frame` | Интервал между renderWorld HEAD; включает ограничения CPU, VSync и ожидания |
| `work/*` | Число операций, не миллисекунды |

GPU-скобки измеряют время между командами, включая возможные простои внутри
интервала. `bake-spot` нельзя выдавать за чистую стоимость треугольников.
GL_TIME_ELAPSED не вкладываются друг в друга. F3 GPU timer вызывает пропуск целого
кадра измерений. Нулевое число принятых кадров — отсутствие измерений, не нулевой cost.

Surface IRL в CR находится в forward material-проходах: эти fullscreen-таймеры
не изолируют его цену. Разность A/B с surface shadows OFF надо мерить при остальных
фиксированных эффектах; её нельзя складывать с разностями VL или считать готовым
per-light бюджетом. Compute-only проходы Iris и его mip-generation перед program.use
этим существующим mixin не охвачены. ProgramSource-хеши относятся к входам Iris,
а не к окончательному GLSL после всех GL-преобразований драйвера.

Подробные таймеры и CSV имеют накладные расходы. Сравнивать одинаковые режимы
измерений; отдельно повторить общий frame-time без detailed/CSV. Во время окна не
менять настройки/разрешение/сцену. Для новой конфигурации начинать новую сессию.
Если профайлер включён после загрузки пака, перезагрузить шейдеры для source-хешей.

PowerShell, JDK 21 установлен в `C:\Program Files\Java\jdk-21`. Target bytecode — 17.
Core main уже выбран под MC 1.20.4; `-Pmc` в этом core не является селектором версии.
Зависимости и Maven вынесены внутрь рабочего каталога:

```powershell

Set-Location "$root\code\irl-core"
```

После следующей правки core надёжнее использовать новую версию артефакта либо
точечно обновить remap-кэш этого core. `publishToMavenLocal` сам по себе не
гарантирует обновление уже ремапнутого JAR. Перед диагнозом сверять runtime resource
и class hash; intermediary-JAR и named dev-JAR могут иметь разные class hashes из-за remap.

## Игровая проверка после подготовки сцены

1. Создать тестовый мир BBS в dev-клиенте 1.20.4. Выбрать указанный CR и фиксировать
   сцену, разрешение, настройки, камеру и VSync. Отдельная сцена: 25 динамических
   спотов. Первый созданный вариант — `New World`, 26 спотов; см. отчёт выше.
2. Снять файловый manifest (не изменяет shaderpacks):

   ```powershell
   .\tools\snapshot-performance-baseline.ps1
   ```

3. Запустить dev-клиент из аддона с теми же JAVA_HOME/GRADLE_USER_HOME:

   ```powershell
   .\gradlew.bat runClient '-Pmc=1.20.4' "-Dmaven.repo.local=$root\.maven-local" '-PclientJvmArgs=-Dirlite.profileVl=true -Dirlite.profileShadowDetail=true -Dirlite.profileCsv=true' --console=plain 2>&1 | Tee-Object -FilePath run/runclient-console.log
   ```

   `-Pquickplay=ИмяМира` можно добавить после создания мира. Для обычного baseline
   **не** включать `profileVlSweep`. Старые IRLite/core JAR в `run/mods` могут мешать
   dev-классам; snapshot ищет их по `fabric.mod.json`, даже если JAR переименован.

4. Проверить `profile-session` (нужный пак, fallback=false, ожидаемый core),
   `profile-source` и путь `profile-csv`. Прогреть сцену, затем записать минимум
   840 кадров и ещё несколько секунд для асинхронного чтения/сброса буфера.
   Лучше выключить профайлер через существующий переключатель, чтобы закрыть файл.
   При выходе из игры последний неполный буфер не использовать.
5. Анализировать нужный CSV, выбрав подходящее начало окна после загрузки мира:

   ```powershell
   .\tools\analyze-profile.ps1 -Capture 'run/logs/irlite-perf/capture-Номер.csv' -WarmupFrames 240 -MeasureFrames 600 -OutputJson build/performance/result.json
   ```

   `captureReachesEnd=true` и `missingGpuFrames=0` требуются для полного окна.
   Анализатор отбрасывает неполные GPU-кадры и показывает число потерь. CPU из
   такого отчёта также относится только к принятым кадрам; при потерях он может
   быть смещён. Односекундные HUD-окна CPU и GPU сдвинуты задержкой GPU-readback,
   для A/B использовать CSV по issue-frame.

## Условия следующих этапов

1а должен отдельно версионировать transform, оценённую позу/кости, morph/scale,
geometry, cutout/material и ресурсные reload. Unknown означает обновлять каждый
кадр, а не считать caster неподвижным. В BBS 2.3.1 ModelForm есть runtime IK,
physics/wind и pose overrides; сериализованный Form или position/yaw недостаточны.
Сохранить очистку после исчезновения caster, tile ownership, world/reset и все
пять инвариантов shadow seam. Не переносить dynamic в static на основании класса.

Проверка bytecode используемого BBS 2.3.1: `ModelFormRenderer.getPose()` объединяет
authored pose и overlays, но не возвращает окончательную позу после animator,
IK, physics и constraints. `renderModel()` сбрасывает флаги их применения для
каждого вызова; `applyPhysicsOnce()` вызывает runtime с entity, tickDelta и
base transform. Поэтому хеш `getPose()` либо Form.toData() сам по себе не даёт
разрешения пропускать overlay. Нужен контракт с фактически оценённым состоянием
отрисовки и invalidation ресурсов; неподдержанный путь остаётся unknown.

Планировщик 1б должен учитывать суммарную цену copy/draw/filters и иметь срок
максимального устаревания, приоритет контакта, обязательное обновление при
движении лампы/смене tile/исчезновении caster и fallback неизвестных поз. Текущий
статический shadowBakeBudget не является бюджетом overlay. Нужна обратная связь
по лампе/роли; агрегаты этапа 0 ещё не являются этим механизмом.

Для point dirty-face сначала описать соседние грани и mip-зависимости. Нельзя
просто обновить одну шестую moment-текстуры и оставить зависимые швы старыми.
Для MSM16 нужен отдельный encoder/decoder и контроль ошибок. Замена RGBA32F на
RGBA16F при текущем EVSM exponent=42 не является корректной оптимизацией.

До froxel VL выбрать художественную модель extinction/per-light density.
Историю сбрасывать при монтаже камеры, перемотке, телепорте, смене позы и резком
изменении света. Для быстрых тонких beams сохранить отдельный путь.

Обязательные игровые сценарии: 25 динамических спотов; point с одной меняющейся
гранью; перекрывающиеся beams; узкие gobo; неподвижные актёры; быстрый фонарик;
крупные BBS-формы; монтаж/перемотка; холодный старт. Проверять контакт на склонах,
кубические швы, исчезнувших caster и прозрачную геометрию. Цели из аудита
14→5–9 мс и VL ×2–4 остаются целями, пока не получены сопоставимые замеры.
