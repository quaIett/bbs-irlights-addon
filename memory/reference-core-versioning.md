Две РАЗНЫЕ оси нумерации, их легко спутать:
- **irl-core (библиотека)**: 1.1 → 1.1.1 → 1.2 → **1.1.3** (2026-07-20) → 1.1.4 → **1.1.5** (2026-07-24, вся ось синхронно на всех ветках core+addon+editor). В mavenLocal лежат все; 1.2 остался как артефакт-ловушка (содержит W2+VRAM-фикс, но НЕ beam-фикс).
- **IRLights (продукт/сборка)**: релиз 1.1.2 = `Desktop/IRLights/IRLights_v1.1.2.zip`. В оси библиотеки 1.1.2 НЕ существовало — ни ветки, ни тега, ни артефакта.

Бамп версии = **5 мест** (ручной, для dev/runClient): `irl-core/gradle.properties` (irl_core_version) + `bbs-irlights-addon/build.gradle` (modClientImplementation + include) + `irlights/build.gradle` (те же две). ГЛАВНОЕ (уточнено 2026-07-24): для **сборки трилогии** версию рулит `BBS/VERSION` — build-trilogy.ps1 ШТАМПУЕТ её во все throw-away worktree (mod_version+irl_core_version+coord), так что коммитить версию в 8 per-MC веток руками НЕ обязательно для релиза; ручной git-бамп веток = только dev-консистентность (runClient берёт gradle.properties, не VERSION). Порт-ветки core (main/1.21.1/1.21.4/1.21.11) держат свою версию независимо — 2026-07-24 все синхронно на 1.1.5. Констрейнтов нет: оба fabric.mod.json объявляют `"irl-core": "*"`, потребители пинят точную координату → понижение номера безопасно.

**Бамп версии ЛЕЧИТ готчу loom-кэша** (re-publish той же версии → подсовывался старый ремапнутый jar, приходилось чистить `.gradle/loom-cache/remapped_mods/.../irl-core-*/<версия>`). Новая координата = новый путь кэша.

**ГОТЧА накопления nested-jar'ов — ПОЙМАНА И ЗАКРЫТА 2026-07-20** (addon f7410b0 / editor cbe3291). Симптом: после бампа координаты инкрементальный build клал в мод-jar И старое, И новое ядро (у редактора было сразу три: 1.1 + 1.1.3 + 1.2), Fabric молча грузит СТАРШЕЕ = устаревший движок. Две независимые протечки, лечить надо обе:
1. `processIncludeJars` стейджит include'ы в `build/processIncludeJars` и НИКОГДА не чистит → jar прошлой координаты остаётся;
2. `remapJar` **дописывает** вложения В СУЩЕСТВУЮЩИЙ выходной jar, а не пишет новый → устаревшая запись выживает даже при чистом стейджинге.
Фикс в обоих build.gradle: `outputs.upToDateWhen{false}` + `doFirst` (purge стейджинга / `delete archiveFile`). Проверено бампом координаты в обе стороны на инкрементальной сборке — ровно одно ядро.
ТУПИК, не повторять: чистка ТОЛЬКО стейджинга не помогает (протечка 2 всё равно тащит старое); тест «подложить jar руками в стейджинг» невалиден — `remapJar` встаёт UP-TO-DATE и вообще не переписывает выходной файл, получается ложный вывод. Валидный тест = реальная смена координаты + инкрементальный build.
**Проверять после каждого бампа**: `unzip -l <jar> | grep irl-core` = РОВНО одна строка.
